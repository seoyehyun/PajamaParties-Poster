# 실험 결과 및 분석

본 문서는 **주파수 민감도, 자원 간 상호작용, KV 오프로딩 및 단계 인식 주파수 관리의 실험 결과**를 제시한다. 실험 주제별로 연구 목적, 측정 조건, 분석 및 근거 CSV를 정리하였다. 실험 플랫폼은 Orange Pi 6 Plus이며 중간 자료의 Firefly 초기 실험과 구분한다.

연구 배경과 사전 지식은 [연구 개요](../README.md)에, 실행 환경과 명령은 [재현 절차](../code/README.md)에 기술하였다. 본 문서의 지표 정의와 비교 기준은 2절에 제시한다.

## 2. 평가 지표 및 비교 기준

### 추론 단계 및 실행 구성

**Prefill**은 입력 문맥을 일괄 처리하는 단계이며, **decode**는 토큰을 순차 생성하는 단계이다. 토큰은 모델의 텍스트 처리 단위이며 7K 문맥은 약 7,000토큰의 입력을 의미한다.

동시 실행은 CPU·GPU·NPU에서 **별도 추론 요청을 함께 처리**하는 실험이다. 하나의 요청을 여러 장치로 나누어 실행한 결과와 구분한다. KV 오프로딩은 CPU 작업에만 적용한다.

`RAM`은 전체 KV를 메모리에서 읽는 기준 방식이며, `swap`은 KV를 NVMe에 보관하고 예측된 그룹을 선택적으로 읽는 방식이다. 어텐션은 다음 토큰 생성 시 이전 문맥 내 각 위치의 참조 가중치를 계산하는 과정이다. `swap` 설정에는 선택적 어텐션과 재사용 버퍼의 효과가 포함되며, 운영체제의 메모리 스왑과 구분한다.

### 주요 지표

| 지표·CSV 열 | 정의 | 해석 기준 |
|---|---|---|
| TTFT · `prefill_s` | 첫 토큰 대기의 대리값으로 사용한 엔진의 입력 처리 시간 | 감소 시 초기 응답 지연이 개선된다. 모델 로드 등 전체 준비 시간은 포함하지 않는다. |
| TPOT · `tpot_ms` | 답변 생성 중 토큰 하나에 걸린 시간(ms/token) | 감소 시 토큰 생성 속도가 개선된다. |
| `gpu_tpot_ms` / `cpu_tpot_ms` | 동시 실행에서 별도로 보고하는 상대 작업의 TPOT | 설정 계열에 따라 주 작업이 다르므로 아래 설명을 확인한다. |
| `vs_naive_*` | 변경 설정의 값 ÷ 같은 묶음의 기준선 값 | 시간·열 면적은 0.81배면 19% 감소, 1.05배면 5% 증가다. |
| `gpu_slowdown` 등 | 동시 TPOT ÷ 단독 TPOT − 1 | 0.20은 단독 실행 대비 처리 시간 1.20배를 의미한다. |
| `heat_area_per_tok` | 입력 처리부터 종료 후 냉각까지의 온도 상승 누적량을 생성 토큰 수로 나눈 값 | 같은 작업·기준선 안에서 비교한다. 단위는 °C·s/token이다. |
| `heat_post_per_tok` | 첫 토큰 이후부터 냉각까지의 열 면적/토큰 | 요청 전체 열 면적과 구간이 다르다. |
| `read_GBps_a720` / `pmu_read_GBps` | CPU 카운터로 추정한 A720의 메모리 읽기량 | GPU·NPU를 포함한 전체 메모리 트래픽은 아니다. |
| `quality` | 열 실험의 판정에 넣은 KV 선택의 어텐션 보존 비중 | 매 실행에서 새로 측정한 답변 정답률이 아니다. |
| `n` / `tail_complete` | 반복 횟수 / 냉각 구간 기록 완료 여부 | n=1은 반복 1회다. 꼬리가 미완료면 열 면적이 덜 계산된다. |

`thermal_ab.py`의 CPU 단독·`ck_` 계열에서 `tpot_ms`와 `prefill_s`는 CPU 작업을 가리킨다. `co_` 계열에서는 GPU 작업을 가리키고 CPU 작업은 별도 열에 적힌다. 동일한 열 이름이라도 설정 계열에 따라 측정 대상이 다르므로 계열 간 직접 비교에서 이를 고려해야 한다.

**열 면적은 온도 상승의 시간 적분값으로, 에너지의 직접 측정값과 구분한다.** 기준 온도 대비 10 °C의 상승이 60초간 유지되는 경우 600 °C·s로 계산된다. 센서별로 실행 전 온도를 기준으로 계산하고, 기준선에서 열 면적이 가장 큰 센서를 대표 지표로 사용한다. 전력 센서가 없어 에너지 직접 측정은 하지 않았다.

후속 열 실험은 TTFT·TPOT이 기준선의 **1.10배 이내**, 품질 입력값이 **0.93 이상**인 설정을 후보로 삼았다. 동시 실행에서는 두 작업의 TPOT을 모두 확인한다. 명확한 열 감소로 판정하려면 최소 5% 차이가 필요하며 반복 간 편차가 크면 더 큰 여유를 둔다. 일부 초기 실험의 판정은 TPOT만을 반영하므로, `verdict`와 함께 TTFT 및 시간 비율을 검토해야 한다.

## 3. 주파수 민감도

### 자원별 주파수 민감도

CPU·GPU의 주 모델은 Qwen3-1.7B Q4_K_M이며, CPU는 A720 8코어, GPU는 Vulkan 경로를 사용하였다. Prefill 처리 속도는 주파수 증가에 따라 향상되었으나, CPU decode는 약 1.5 GHz 이후 추가적인 성능 향상이 제한되었다. 해당 구간의 CPU 메모리 읽기량은 약 39~44 GB/s였다. GPU decode는 상대적으로 높은 주파수 민감도를 보였다.

주파수 민감도 분석의 정규화 가로축은 `현재 주파수 ÷ 해당 장치의 최대 주파수`, 세로축은 `현재 속도 ÷ 최대 주파수에서의 속도`로 정의한다. 각 곡선은 주파수 변화에 대한 성능 민감도를 나타내며 장치 간 절대 성능 비교에는 사용하지 않는다.

근거: [CPU 주파수 스윕](csv/cpufreq_sweep_20261113_summary.csv), [GPU 주파수 스윕](csv/gpufreq_sweep_20261113_summary.csv), [메모리 읽기량 보정](csv/membw_calib_20261113.csv).

NPU는 Qwen2.5-0.5B int8을 사용하였으므로, 다음 값은 NPU 내부의 주파수별 성능 변화로 해석한다.

| NPU 주파수 | decode 속도 | prefill 속도 |
|---|---:|---:|
| 400 MHz | 11.7 tokens/s | 448 tokens/s |
| 600 MHz | 14.6 tokens/s | 650 tokens/s |
| 800 MHz | 16.5 tokens/s | 834 tokens/s |
| 1200 MHz | 18.3 tokens/s | 1116 tokens/s |

주파수 3배 증가 시 prefill 처리량은 2.49배, decode 처리량은 1.56배 증가하였다. decode에는 주파수와 무관한 호스트 CPU 작업도 포함된다. 근거: [NPU decode](csv/npu_decode_summary.csv), [NPU prefill](csv/npu_prefill_summary.csv).

## 4. 자원 간 상호작용

### RI 행렬 정의

행은 **주파수를 바꾼 자원**, 열은 **성능을 관찰한 자원**이다. RI 행렬의 각 셀은 `d ln(perf) / d ln(freq)`로, 주파수의 상대적 변화에 대해 성능이 얼마나 변하는지를 나타내는 기울기다. 양수는 주파수를 높일수록 성능도 높아지는 관계, 음수는 상대 성능이 떨어지는 관계, `~0`은 영향이 작은 관계를 의미한다. CPU 주파수 → GPU 성능의 −0.57은 변화 방향과 민감도를 나타내며, GPU 슬로다운 57%와는 다른 지표이다.

단독 실행에서는 대각선, 즉 각 자원의 자체 주파수 영향이 주로 보인다. Decode 동시 실행에서는 CPU 주파수 → GPU·NPU 성능 칸이 음수로 나타난다. `n/m`은 NPU 유휴 조건에서 직접 측정하지 않은 항목이며, 0으로 측정된 항목과 구분한다.

최종 RI는 CPU·GPU·NPU의 **3×3 행렬**이다. 중간 자료에서 계획한 Memory 포함 4×4 RI와 구분한다. 메모리 주파수는 직접 바꿀 수 없어 메모리 축은 CPU 읽기량으로 간접 분석하였다. 아래의 “4×4”는 CPU 주파수 네 점 × GPU 주파수 네 점의 **16개 실험 조합**을 의미한다.

### 동시 실행 간섭

CPU {1200, 1500, 1800, 2200 MHz} × GPU {350, 600, 800, 1000 MHz}를 비교하였다. CPU·GPU decode 동시 실행에서 두 자원의 주파수 증가에 따라 GPU 간섭이 확대되었으며, GPU 슬로다운은 최대 **+74.6%**였다. 같은 4×4 조합의 prefill 간섭은 0.5% 이내였다.

근거: [초기 조합](csv/corun_20261113_summary.csv), [중간 CPU 주파수 E4](csv/e4_decode_mid_summary.csv), [GPU 800 MHz 추가점](csv/e4_decode_800_summary.csv), [prefill 4×4](csv/e4_prefill_4x4_summary.csv).

NPU·CPU decode 동시 실행에서 NPU 슬로다운은 최대 +16.6%로 측정되었다. NPU 연산 시간보다 호스트 CPU 처리 시간이 늘어나, 호스트 쪽 메모리 경합이 주요 원인이라는 해석을 지지한다. NPU·GPU 조합은 측정한 조건에서 간섭이 작았다. 세 자원 동시 실행도 [NPU decode 데이터](csv/npu_decode_sweep.csv)에 포함되어 있다.

NPU 발열 차이는 1 °C 해상도의 온도 센서로 구분할 수 없었다. 따라서 NPU 주파수의 열 최적값은 이 자료로 정하지 않았다.

## 5. KV 오프로딩의 효과

### CPU 읽기량과 주파수 민감도 — E5

입력 7,013토큰 + 생성 2,000토큰, prefill은 기본 정책, 첫 토큰부터 A720 주파수를 고정하였다.

| CPU 주파수 | RAM TPOT | 오프로딩 TPOT | CPU 읽기량 RAM → 오프로딩 |
|---|---:|---:|---:|
| 1.2 GHz | 85.6 ms | 86.5 ms | 38.7 → 19.7 GB/s |
| 1.8 GHz | 75.0 ms | 68.8 ms | 43.3 → 24.7 GB/s |
| 2.2 GHz | 73.6 ms | 65.6 ms | 43.6 → 26.5 GB/s |

오프로딩 적용 시 CPU 읽기량은 약 40~50% 감소하였으며, 높은 주파수에서 성능 개선 폭이 증가하였다. 2.2 GHz의 TPOT은 약 11% 단축되었으나, 1.2 GHz에서는 KV 선택·관리 비용에 따른 속도 개선이 관찰되지 않았다. RAM 설정보다 오프로딩 설정의 주파수 증가 효과가 크게 나타나, **대역폭 병목에서 연산 쪽으로의 이동**이라는 해석을 지지한다.

1.5 GHz의 속도 측정값은 이전 [단계별 측정](csv/thermal_ab_phase_20261114_summary.csv)의 `phase_1500`·`kvphase_1500`을 재사용하였다. E5 데이터의 1.5 GHz 항목은 해당 기존 측정으로 보완된다.

근거: [E5 설정별 요약](csv/e5_summary.csv), [실행별 값](csv/e5_runs.csv). 이 실험의 냉각 기록은 3분으로 제한했으므로 열 면적을 최종 발열 비교에 쓰지 않는다.

### 문맥 길이에 따른 GPU 간섭 변화

CPU 1.5 GHz·GPU 1 GHz에서 CPU 입력 문맥을 바꾸고, RAM KV와 오프로딩을 각각 2회씩 비교하였다.

| CPU 문맥 | GPU 슬로다운: RAM → 오프로딩 | CPU 동시 실행 TPOT: RAM → 오프로딩 |
|---|---:|---:|
| 약 3K | +43% → +24% | 57.1 → 69.6 ms |
| 약 7K | +64% → +19% | 81.0 → 83.0 ms |
| 약 11K | +87% → +17% | 106.1 → 90.4 ms |

GPU 지연은 모든 문맥 길이에서 감소하였으나, CPU TPOT은 3K에서 증가하고 11K에서 감소하였다. 따라서 GPU 간섭 감소와 CPU 자체 성능 개선은 별도의 평가 항목으로 구분한다.

11K 문맥의 **CPU 단독 구간**에서 `cpu_solo_ms`는 101.1 → 87.75 ms/token으로 **13.2% 단축**되었다. 3K의 약 22% 성능 저하 역시 단독 구간 53.46 → 65.07 ms/token을 기준으로 한다. 표의 `cpu_corun_ms`는 **GPU 동시 실행 구간**의 값으로, 단독 구간 지표와 구분한다.

근거: [문맥 길이별 요약](csv/corun_kvswap_ctx_20261119_summary.csv). 다른 주파수 네 조합에서도 GPU 간섭 감소를 확인한 결과는 [E8 요약](csv/e8_7k_summary.csv)과 [구간별 측정](csv/e8_7k_windows.csv)에 있다.

## 6. 성능·발열 상충관계

### CPU 단독 실행 — 7K 입력·2,000토큰 생성

기준선은 RAM KV·기본 주파수 정책이다. 1.00배보다 작은 시간·열 면적은 개선을 의미한다.

| 설정 | TTFT 비율 | TPOT 비율 | 요청 전체 열 비율 | 반복 |
|---|---:|---:|---:|---:|
| RAM KV·기본 정책 | 1.00 | 1.00 | 1.00 | 2회 |
| RAM KV·요청 전체 CPU 1.5 GHz * | 1.506 | 1.053 | 0.714 | 2회 |
| RAM KV·decode만 CPU 1.5 GHz | **1.003** | **1.052** | **0.874** | 2회 |
| KV 오프로딩·기본 정책 | 1.042 | 0.896 | 0.903 | 2회 |
| KV 오프로딩·decode만 CPU 1.5 GHz | 1.044 | 1.026 | 0.904 | 1회 |

Decode에만 1.5 GHz를 적용한 경우 TTFT를 유지하면서 **전체 열 면적이 12.6% 감소하였다.** 요청 전체에 1.5 GHz를 적용한 경우 열 면적은 약 28.6% 감소하였으나 TTFT가 50.6% 증가하여 성능 제약을 초과하였다.

별표(*)는 별도 측정 묶음의 결과를 나타낸다. 전체 1.5 GHz 행은 11/13 묶음, 나머지는 11/14 묶음이며, 각 묶음의 RAM 기본 설정 대비 비율로 표시한다. 열 절대값을 서로 합치거나 나누어 새 비율을 만들지 않는다.

근거: [11/14 단계별 결과](csv/thermal_ab_phase_20261114_summary.csv), [11/13 전체 주파수 고정 결과](csv/thermal_ab_20261113_summary.csv).

위 표의 KV 오프로딩 + decode 행은 당시의 1회 측정이다. 이후 자동 설정표를 정하기 위해 기본 주파수와 decode만 1.5 GHz를 다시 2회씩 비교한 결과, 후자의 decode 구간 열은 약 25% 낮았다. 요청 전체 열 차이는 약 5%였으며, 이는 두 설정에 공통인 prefill의 높은 비중에 기인한다. 이 재측정을 반영해 자동 설정표도 수정하였다. 근거: [설정별 요약](csv/kvphase_ab_summary.csv), [단계별 열을 포함한 실행별 값](csv/kvphase_ab_runs.csv).

### 긴 CPU 문맥과 GPU 동시 실행 — E7

CPU 요청은 7K 입력 + 3,000토큰 생성이다. CPU의 첫 토큰부터 GPU 요청 3,000토큰 생성을 시작한다. 기준선은 RAM KV·기본 주파수 정책이다. 별표 행을 제외하면 각 설정 1회 측정이다.

| 설정 | CPU TPOT 비율 | GPU TPOT 비율 | CPU TTFT 비율 | 전체 열 비율 | 첫 토큰 이후 열 비율 |
|---|---:|---:|---:|---:|---:|
| RAM KV·기본 정책 | 1.00 | 1.00 | 1.00 | 1.00 | 1.00 |
| RAM KV·GPU 1 GHz·요청 전체 CPU 1.5 GHz * | 1.07 | 0.94 | 1.51 | 0.71 | 0.72 |
| 오프로딩·GPU 1 GHz·CPU 기본 | 0.84 | 0.81 | 1.04 | 0.90 | 0.76 |
| 오프로딩·GPU 1 GHz·CPU는 decode만 1.5 GHz | **0.97** | **0.79** | **1.05** | **0.81** | **0.55** |

마지막 설정은 두 작업의 TPOT과 첫 토큰 대기 조건을 모두 통과하면서 **요청 전체 열 면적을 약 19% 줄였다.** 첫 토큰 이후 열 0.55배는 다른 측정 구간의 수치다.

근거: [E7 요약](csv/e7_ck_summary.csv), [E7 실행별 기록](csv/e7_ck_runs.csv). 설정 이름은 마지막 행이 `ck_swap_g1000_d1500`이다. 별표 행 `ck_ram_g1000_c1500`은 별도 11/19 묶음의 2회 평균이며, 그 묶음의 RAM 기준선 대비 비율이다. 근거는 [11/19 동시 실행](csv/thermal_ab_ck_20261119_summary.csv)에 있다.

### GPU 단독 및 짧은 문맥 동시 실행

GPU 단독 실행에서 주파수 제한은 실행 시간과 열 면적을 모두 증가시켰다. GPU 800 MHz 이하에서는 TPOT도 기준선의 1.10배를 넘었다. 따라서 CPU decode에서 유리했던 “주파수 낮추기”를 GPU에 그대로 적용할 수 없었다. 근거: [GPU 단독](csv/thermal_ab_gpu_20261118_summary.csv).

짧은 CPU 요청들과 GPU 요청을 함께 실행한 경우에는 CPU 1.5 GHz에서 GPU와 열은 개선되었지만 CPU TPOT이 속도 조건을 근소하게 넘었다. 초기 값은 1.12배, 재측정은 약 1.10~1.11배다. 해당 결과는 E7의 긴 문맥 동시 실행 결과와 구분하여 해석한다. 근거: [초기 동시 실행](csv/thermal_ab_co_20261118_summary.csv), [재측정](csv/e6_co2_summary.csv).

긴 문맥에서 CPU 주파수를 요청 전체에 고정한 선행 비교는 [thermal_ab_ck 요약](csv/thermal_ab_ck_20261119_summary.csv)에 있다.

## 7. Governor-lite — 단계 인식 주파수 관리

자동 주파수 관리의 동작 순서는 **상태 감지 → 테이블 조회 → 주파수 적용 → 효과 검증**이다.

| 단계 | 구현 동작 |
|---|---|
| 상태 감지 | 0.5초마다 CPU 사용률·출력 파일과 GPU 활동 상태를 확인해 CPU prefill/decode와 GPU 작업 유무를 구분한다. |
| 테이블 조회 | 현재 CPU 단계, GPU 동작 여부, 미리 지정한 KV 위치에 해당하는 규칙을 고른다. |
| 주파수 적용 | Prefill은 기본 정책, KV 오프로딩의 decode는 A720 1.5 GHz로 전환한다. GPU·NPU 주파수와 KV 위치는 직접 바꾸지 않는다. |
| 효과 검증 | 같은 작업량의 RAM 기준선, KV 오프로딩만 사용한 설정, 단계별 고정 설정과 비교한다. |

[초기 사전 테이블 CSV](csv/precomputed_table_20261118.csv)에는 당시의 측정값과 일부 후속 재측정이 함께 들어 있다. 실제 자동 적용의 규칙은 [governor 코드](../code/scripts/joint/governor_lite.py)에서 확인한다. 최종 KV 오프로딩 규칙은 prefill 때 기본 정책, decode 때 1.5 GHz이다.

수정 후 비교 실험은 CPU 7K 입력·6,500토큰 생성 중 GPU 700토큰 요청을 세 차례 실행하여 **모든 설정의 작업량을 동일하게 구성하였다.** 아래는 설정당 1회 측정이며, 열 값은 첫 토큰 이후의 토큰당 누적량이다.

| 설정 | 첫 토큰 이후 열 (°C·s/token) | CPU TPOT | GPU TPOT |
|---|---:|---:|---:|
| RAM 기준선 | 2.83 | 92.9 ms | 88.4 ms |
| KV 오프로딩·CPU 기본 | 1.43 | 66.0 ms | 58.5 ms |
| KV 오프로딩·decode만 CPU 1.5 GHz | 0.92 | 76.6 ms | 52.6 ms |
| KV 오프로딩·자동 적용 | **0.92** | **76.7 ms** | **52.7 ms** |

자동 적용은 단계별 고정 설정인 **decode 1.5 GHz와 유사한 결과**를 보였다. **KV 오프로딩 단독 적용 설정 대비** TTFT는 346.4초로 유지되었으며, 첫 토큰 이후 열 면적은 1.426 → 0.9157로 약 **36% 감소**하였다. CPU TPOT은 65.98 → 76.67 ms로 약 **16% 증가**, GPU TPOT은 58.54 → 52.71 ms로 약 **10% 감소**하였다.

CPU TPOT의 16% 증가는 KV 오프로딩 단독 적용 설정을 비교 기준으로 한다. RAM 기준선 대비 비율은 76.67 ÷ 92.91 ≈ 0.83배로, CPU TPOT이 감소한 결과이다. 속도 제약의 판정 기준선과 성능·발열 상충관계의 비교 기준은 구분하여 적용한다.

이 시나리오의 장점은 단계 전환의 자동 적용이다. E7의 19%는 RAM 기본 대비 **요청 전체** 열 면적이고, 여기의 36%는 KV 오프로딩만 사용한 설정 대비 **첫 토큰 이후** 열 면적이다. 서로 다른 비교 대상·구간·작업량의 수치다.

근거: [수정 후 gov2 요약](csv/gov2_summary.csv), [실행별 기록](csv/gov2_runs.csv), [결과 그림](csv/gov2.png). 기준선의 냉각 꼬리는 기록 제한 안에 끝나지 않아 열이 과소 계산되었으며, KV 오프로딩 설정끼리의 비교에는 이 문제가 없다.

[첫 실행 gov 요약](csv/gov_summary.csv)과 [그림](csv/gov.png)도 보관되어 있다. 첫 실행은 설정별 GPU 작업 수가 같지 않았고 이후 규칙도 수정했으므로 최종 성능 비교에는 gov2를 사용한다.

## 8. 보조 실험 — 품질 및 소형 모델

다음 보조 실험은 주된 1.7B 성능·발열 결과를 보완한다. NPU 주파수 스윕의 0.5B int8 실험과 CPU용 0.5B Q4_K_M 실험은 별도 실험으로 구분한다.

### NIAH 기반 KV 선택 품질 평가

NIAH는 장문 내에 삽입한 특정 정보를 검색하도록 구성한 평가이다. 약 4K 문맥의 서로 다른 위치에 이름별 7자리 암호를 삽입한 15문항을 사용하였다.

| KV 선택 방식 | 맞힌 문항 |
|---|---:|
| 전체 어텐션 | 15/15 |
| 균등 선택 | 0/15 |
| 예측기 r=128 | 15/15 |
| 예측기 r=32 | 15/15 |

근거: [문항별 결과 CSV](csv/kvswap_niah_4k_20261107.csv). 이 검사는 KV를 RAM에 둔 상태에서 선택 방식의 품질을 확인하였다. 특정 정보 찾기 검사이므로 요약·추론 등 다른 작업의 품질까지 보장하지 않는다.

열 실험의 `quality=0.9448`과 NIAH 정답률은 별도 지표이다. 전자는 앞선 실험에서 측정한 **어텐션 보존 비중을 코드에 입력한 값**이며, 산출 당시의 원본은 이 배포본에 포함되어 있지 않다. 정의와 출처 설명은 [thermal_ab.py](../code/scripts/joint/thermal_ab.py) 상단에 있다. 초기 열 실험은 입력값 0.937을 사용하였다.

### 소형 모델의 문맥 길이별 성능 평가 — E9

Qwen2.5-0.5B Q4_K_M에서 문맥 길이를 변경하며 1,000토큰을 생성하였다. 각 설정은 1회 측정이다.

| 문맥 | RAM TPOT | 오프로딩 TPOT | TPOT 비율 | 데이터 |
|---|---:|---:|---:|---|
| 약 256토큰 | 13.5 ms | 15.2 ms | 1.13 | [256 결과](csv/e9_256_summary.csv) |
| 약 4K | 19.3 ms | 17.0 ms | 0.88 | [4K 결과](csv/e9_4k_summary.csv) |
| 약 16K | 42.0 ms | 18.2 ms | 0.43 | [16K 결과](csv/e9_16k_summary.csv) |

속도상 손익분기점은 256과 4K 사이이며 정확한 위치는 미측정이다. 이 모델은 예측기 r=32, 그룹 크기 G=16, 선택 그룹 M=25를 사용해 주된 1.7B 실험과 설정도 다르다.

긴 문맥에서 디스크 읽기는 1,000스텝당 약 0.8 MiB로 매우 적었다. 따라서 주된 이득은 선택적 읽기와 KV 재사용으로 해석한다. **0.5B 모델의 답변 품질은 별도로 측정하지 않았다.** CSV의 품질 입력값 0.9448은 해당 모델의 실측 품질로 해석하지 않는다.

E 번호는 실행 계획의 식별자다. 이 문서의 절 번호와 일치하지 않는다.

## 10. 분석 한계 및 제외 항목

- **반복 수:** 11/20~21 보강 실험에서 새로 측정한 점은 대체로 n=1이다. 기존 값의 재사용과 이후 n=2 재측정이 섞여 있으므로 파일의 반복 수를 확인한다.
- **열 비교:** 서로 다른 묶음의 시작 온도·요청 구성이 달라 열 절대값을 비교하지 않는다. E7의 전체 열 0.81배와 governor의 첫 토큰 이후 열 0.32배는 작업량·구간이 달라 우열 비교에 쓸 수 없다.
- **사용률 오류:** `e6_co`의 decode 사용률 구간에는 GPU 작업이 끝난 뒤의 시간이 섞였다. 사용률은 `e6_co2`를 사용한다.
- **전환 오차:** `ck_` 설정의 `switch_error_s`는 CPU·GPU 종료 시각 차이 때문에 잘못 계산될 수 있어 해석에 사용하지 않는다.
- **대역폭 범위:** CPU 카운터가 보지 못하는 GPU·NPU의 트래픽은 직접 측정하지 않았다. `bus_GBps_*`는 다른 접근도 포함하는 상한 성격의 값이므로 CPU 읽기량과 대체하지 않는다.
- **품질 범위:** 보존 비중의 입력값과 15문항 NIAH는 전체 설정·문맥·작업의 품질 검증을 대신하지 않는다. 작은 모델과 NPU의 품질은 별도 평가가 필요하다.
