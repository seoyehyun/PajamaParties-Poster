# CPU, GPU 주파수 스윕과 메모리 (Orange Pi 6 Plus, 2026-11-13)

A720 CPU 주파수와 GPU 주파수를 한 번에 하나씩 바꿔 가며 CPU 실행, GPU 실행, 메모리 대역폭을 쟀고, 두 워크로드를 동시에 돌렸을 때의 간섭도 쟀다. NPU는 넣지 않았다. 메모리 대역폭은 코어 PMU(perf)를 `membw_probe`로 보정해서 구했다. 원본 출력은 보드의 `~/sweep_runs/runs/`와 저장소의 `runs/`(git 제외)에 있고, 폴더 이름의 날짜(`20261110`)는 보드 시계라서 실제 날짜와 3일 어긋난다.

## 1. A720 주파수 스윕 (3회 평균)

| A720 MHz | CPU decode ms/tok | decode 읽기 대역폭(PMU) | decode 추정 대역폭 | probe 읽기 천장 | CPU prefill ms/tok | GPU decode ms/tok | GPU prefill ms/tok |
|---|---|---|---|---|---|---|---|
| 800 | 79.9 | 14.8 GB/s | 16.0 | 18.2 | 19.8 | 37.60 | 54.62 |
| 1000 | 53.7 | 21.9 | 23.8 | 25.4 | 13.2 | 37.28 | 54.70 |
| 1200 | 38.0 | 30.7 | 33.6 | 38.5 | 13.0 | 37.13 | 54.70 |
| 1500 | 33.3 | 35.1 | 38.3 | 38.9 | 10.5 | 37.09 | 54.70 |
| 1800 | 31.2 | 37.6 | 41.0 | 39.3 | 8.8 | 37.03 | 54.74 |
| 2200 | 30.7 | 38.5 | 41.6 | 39.7 | 7.2 | 36.95 | 54.65 |

- **CPU 주파수는 GPU 성능에 거의 영향이 없다.** 800 → 2200 MHz(2.75배)에서 GPU decode가 37.60 → 36.95 ms/tok(약 1.7%), prefill은 변화 없음. 반복 간 편차(0.1~0.5%)와 같은 수준이다.
- **CPU decode의 무릎은 약 1.5~1.8 GHz다.** 1800 → 2200 MHz는 1.6% 차이뿐이다. 읽기 대역폭은 1.8 GHz에서 천장(probe 읽기 약 39~40 GB/s)에 닿는다. 단순 읽기 probe의 무릎(1.2 GHz)보다 높은 것은 Q4_K 역양자화 연산이 더해지기 때문으로 보이지만 확인하지 못했다.
- **probe 대역폭은 1.0 → 1.2 GHz 사이에서 꺾인다.** 읽기 25.4 → 38.5, 쓰기 29.7 → 55.3 GB/s이고 그 위로는 평평하다(쓰기 천장 약 56 GB/s). 다만 1.0 GHz 요청은 코어가 실제 1.2 GHz로 돌았을 가능성이 크다(5절). prefill이 1.0과 1.2 GHz 요청에서 거의 같은 것(13.2 vs 13.0 ms/tok)도 그 때문으로 보인다. 그런데도 메모리 대역폭이 크게 다른 이유는 확인하지 못했다.
- **prefill은 연산 바운드다.** ms/tok이 주파수에 거의 비례하고(19.8 → 7.2, 2.75배) 메모리 읽기는 2.0~5.4 GB/s로 낮다.
- **LLC-load-misses 비율은 주파수와 무관한 구조적 값이다.** decode 0.96~0.98(가중치를 스트리밍), prefill 약 0.69.
- `stall_backend_mem` 비율은 단조롭지 않다(800 MHz 0.33, 1200 MHz 0.09, 2200 MHz 0.38). 원인을 모르니 해석에 쓰지 않는다.

## 2. GPU 주파수 스윕 (2회 평균, A720 2200 MHz 고정)

| GPU MHz | GPU decode ms/tok | GPU prefill ms/tok | GPU decode 추정 대역폭 | clpeak 전역 메모리 대역폭 | CPU decode ms/tok | CPU decode 읽기(PMU) | probe 읽기 |
|---|---|---|---|---|---|---|---|
| 216 | 152.4 | 242.8 | 8.4 GB/s | 21.1 | 30.68 | 38.47 | 39.7 |
| 350 | 97.6 | 157.2 | 13.1 | 35.9 | 30.69 | 38.46 | 39.7 |
| 600 | 58.1 | 91.5 | 22.0 | 48.1 | 30.72 | 38.45 | 39.7 |
| 800 | 44.4 | 68.5 | 28.8 | 48.7 | 30.67 | 38.49 | 39.7 |
| 1000 | 36.8 | 54.8 | 34.7 | 48.8 | 30.69 | 38.45 | 39.8 |

- **GPU 성능은 GPU 주파수에 거의 비례한다.** 216 → 1000 MHz(4.6배)에서 decode 4.1배, prefill 4.4배 빨라진다. GPU decode의 실제 대역폭 사용(최대 34.7 GB/s)은 clpeak 천장(48.8 GB/s)에 못 미쳐서 연산 쪽이 한계다.
- **GPU의 메모리 대역폭 천장은 600 MHz에서 포화한다**(clpeak 48.1 → 48.8 GB/s). GPU 성능은 그 뒤로도 계속 오른다.
- **CPU 성능은 GPU 주파수와 무관하다.** CPU decode 30.62~30.80 ms/tok, 읽기 대역폭, LLC miss 비율 모두 평평하다. 이건 GPU가 놀고 있을 때의 대조 결과다.
- 1과 2를 합치면 **한쪽만 돌릴 때는 CPU와 GPU가 DVFS 관점에서 독립**이다.

## 3. CPU와 GPU 동시 실행 (2회 평균)

CPU decode와 GPU decode를 동시에 돌렸다. 슬로다운은 같은 주파수에서의 `동시 ms/tok ÷ 단독 ms/tok − 1`이다. 두 반복의 값이 1.5% 안에서 일치한다.

| A720 MHz | GPU MHz | CPU 단독 → 동시 (ms/tok) | GPU 단독 → 동시 (ms/tok) | 추정 대역폭 CPU + GPU (동시) |
|---|---|---|---|---|
| 1200 | 350 | 37.80 → 38.25 (+1.2%) | 99.7 → 102.5 (+2.8%) | 33.4 + 12.5 = 45.8 GB/s |
| 1200 | 600 | 37.80 → 39.17 (+3.6%) | 59.8 → 63.8 (+6.7%) | 32.6 + 20.0 = 52.6 |
| 1200 | 1000 | 37.80 → 40.28 (+6.6%) | 37.7 → 45.0 (**+19.6%**) | 31.7 + 28.3 = 60.0 |
| 2200 | 350 | 30.61 → 30.19 (−1.4%) | 99.7 → 135.8 (**+36.2%**) | 42.3 + 9.4 = 51.7 |
| 2200 | 600 | 30.61 → 30.55 (−0.2%) | 59.8 → 93.1 (**+55.8%**) | 41.8 + 13.7 = 55.5 |
| 2200 | 1000 | 30.61 → 31.06 (+1.5%) | 37.7 → 65.8 (**+74.6%**) | 41.1 + 19.4 = 60.5 |

- **한쪽만 크게 느려진다.** GPU가 최대 +75% 느려지는 동안 CPU는 −1.4~+6.6%다. 메모리 경합에서 CPU가 우선하는 것으로 보이지만 원인은 확인하지 못했다.
- **CPU 주파수가 GPU 피해를 좌우한다.** GPU 1000 MHz에서 A720이 2.2 GHz면 +75%, 1.2 GHz면 +20%다. 단독 스윕에서 평평하던 교차 효과가 동시 실행에서 나타난다.
- **추정 대역폭의 합은 GPU 1000 MHz에서 약 60 GB/s로 포화하는 것처럼 보인다**(A720 두 설정 모두 60.0, 60.5). 모델 크기 × tokens/s로 계산한 추정치라 DRAM 한계로 단정할 수 없다. 합이 51.7인 GPU 350 MHz 점에서도 이미 +36%라서 단순한 합 상한만으로 설명되지 않는다.
- **트레이드오프.** GPU 1000 MHz에서 A720을 2.2 → 1.2 GHz로 내리면 CPU는 31.1 → 40.3 ms(+30%) 느려지고 GPU는 65.8 → 45.0 ms(−32%) 빨라진다. 두 토큰 처리량의 합은 47.4 → 47.0 t/s로 거의 같다. GPU 600 MHz에서는 합이 43.5 → 41.2 t/s로 5% 줄어서 모든 점에서 성립하지 않는다. CPU 주파수를 낮추면 전력이 줄 텐데 측정하지 못했다.

## 4. 메모리 대역폭 측정: PMU 보정

이 보드에는 uncore PMU(CMN, DDR 컨트롤러)가 없다. 코어 PMU(`armv8_pmuv3_0` = A720 8코어)로 트래픽을 추정하려고, 알려진 양을 스트리밍하는 `membw_probe`(읽기, 쓰기, 복사, triad)로 이벤트 하나가 몇 바이트에 해당하는지 구했다. 1·8스레드 × 2.2·1.2 GHz × 4패턴 16개 설정이다. 카운터는 반복 횟수 차이(3회와 23회)로 구해 초기화를 상쇄했다.

| 카운터 | 이벤트 1개당 스트리밍 바이트 | 판정 |
|---|---|---|
| `bus_access` | 30.4 ~ 31.9 B (16개 설정 전부) | 순수 스트리밍에서 총 트래픽(읽기+쓰기)으로 환산 가능(31.5 B) |
| `l2d_cache_refill` | 읽기 63.9, triad 95.9, copy 127.9 | 읽은 바이트 = refill × 64 B. 읽기 대역폭에 쓴다 |
| `ll_cache_miss_rd` (= LLC-load-misses) | 241 ~ 14,216 B (읽기·복사·triad), 쓰기는 사실상 0 | 대역폭 환산 불가. 프리페처가 못 가린 demand 읽기만 센다 |
| `l3d_cache_refill`, `l2d_cache_wb` | 279 ~ 2.7M B, 1.3K ~ 24K B | 쓸 수 없음 |

- 8스레드 대역폭 천장: 읽기 38.6~39.7, 복사 42.6~42.7, triad 38.8~39.8, 쓰기 55~56 GB/s. 1스레드는 주파수에 비례한다(읽기 9.5 → 17.5 GB/s).
- **정정(스윕으로 확인).** `bus_access` 환산은 순수 스트리밍에서만 맞다. llama decode에서는 모델 크기 × tokens/s의 약 1.5배(63 vs 41.6 GB/s)가 나와 DRAM에 닿지 않는 트래픽(L3 히트나 코어 간 공유 데이터로 추정, 미확인)을 함께 세는 것으로 보인다. `총 − 읽기`로 구한 쓰기는 decode에서 25 GB/s가 나와 가능하지 않은 값이었다. 그래서 스윕 스크립트는 **읽기(`l2d_cache_refill × 64`)를 주 지표**로, `bus_access`는 상한 참고값(`pmu_bus_GBps`)으로만 기록하고 쓰기 열은 뺐다. 읽기 값은 decode에서 추정치와 약 10% 안에서 맞았다(38.5 vs 41.6 GB/s).
- GPU 실행은 PMU로 트래픽을 볼 수 없어서(호스트 코어 몫은 잡음 수준) 추정 대역폭과 clpeak만 쓴다.
- 보정 첫 시도는 `sudo perf stat -o`가 일반 사용자 임시 파일에 쓰지 못해(`fs.protected_regular`) 전부 조용히 실패했다. 표준 에러를 셸에서 리다이렉션하는 방식으로 고쳐 다시 돌렸다.

## 5. 한계와 주의

- **주파수 축은 요청값이다.** 실제 코어 주파수는 11/10 단계 탐색([freq_steps_20261110.csv](../csv/freq_steps_20261110.csv), CPPC 피드백 카운터 기준)으로 보면 800, 1500 MHz 요청은 4개 정책이 모두 그대로이고, **1000 요청은 전 정책이 1200**, 1200 요청은 cpu0-1만 1500(나머지 1200), 1800 요청은 cpu0-1과 cpu10-11이 1900(나머지 1800), 2200 요청은 cpu0-1이 2500(나머지 2200)으로 돈다. 코어 클럭이 요청과 다른 점이 있어서 "무릎 약 1.5~1.8 GHz" 같은 값은 요청 기준의 근사다. 1500 MHz는 정확하다. 실제 주파수 검증(`acpi_cppc/feedback_ctrs`, [freq_steps.sh](../../code/scripts/sweep/freq_steps.sh)처럼)을 스윕 스크립트에 넣는 것이 후속 과제다.
- 모델 하나, prefill 128토큰과 decode 32토큰(GPU 동시 실행은 64토큰 × 8회)이다. 컨텍스트가 길어지면 달라질 수 있다.
- 동시 실행은 decode만 쟀다. prefill 동시 실행은 하지 않았다.
- GPU 실행의 메모리 지표는 clpeak(합성)과 모델 크기 × t/s 추정이고, DRAM 이론 한계는 모른다.
- 전력은 재지 않았다. J/token, PPR은 없다.
- 동시 실행의 CPU 값은 GPU 구간에 완전히 들어간 반복만 쓴다. GPU 프로세스 시작(모델 로드) 구간을 건너뛰도록 6초를 제외했고, 이 값은 임의 선택이다.
- 반복이 2~3회라 분포를 말할 수는 없다. 편차는 작았다.
