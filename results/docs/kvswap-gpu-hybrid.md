# KVSwap을 GPU와 함께 쓰는 구성 시험 (Orange Pi 6 Plus, 2026-11-08)

KVSwap을 CPU 전용이 아니라 GPU(Mali-G720, Vulkan)와 함께 쓸 수 있는지 시험했다. 결론은 **동작은 하지만 이 보드에서는 CPU 전용보다 2~4배 느리다**이다.

## 구성

llama.cpp의 `-ngl 99 -nkvo`를 쓴다. 가중치 연산(Q/K/V 프로젝션, FFN, 출력)은 GPU, KV cache는 CPU 메모리(direct I/O면 NVMe가 원본)에 둔다.

시험하면서 확인한 점은 다음과 같다.

- **`-nkvo`에서도 flash attention은 GPU에서 돈다.** 이 버전의 llama.cpp는 flash attention을 쓰지 않는 경로에서만 어텐션을 CPU에 고정한다. FA 경로에서는 스케줄러가 레이어마다 KV 뷰 전체를 GPU로 복사하고, 마스크는 그래프당 한 번만 GPU로 올린다. 그래서 레이어별 선택이 GPU에 전달되지 않았고, 예측기의 RAM 실행과 NVMe 실행의 출력이 달랐다.
- 패치 04에서 KVSwap 선택이 켜져 있으면 `-nkvo`일 때 FA 노드를 CPU에 고정하도록 했다. 일반 실행(선택 없음)의 동작은 바꾸지 않았다.
- 같은 패치에서 레이어 i의 마스크를 레이어 i-1의 어텐션이 끝난 직후에 쓰도록 바꿨다. 예측기가 GPU에서 계산한 근사 Q는 `ggml_backend_tensor_get`으로 복사해 읽는다.

결과적으로 GPU는 행렬 곱, CPU는 어텐션과 KV 선택과 I/O를 맡는다. 레이어마다 GPU 구간과 CPU 구간이 번갈아 실행된다(그래프 분할 58개, 28개 레이어).

## 결과

Qwen3-1.7B Q4_K_M, 약 1.2K토큰 프롬프트, `-c 2048`, 32토큰 생성, cpu6-9 4스레드, M=50, G=8, W=256, 예측기 r=128, 1회 실행.

| 구성 | RAM decode ms/token | NVMe decode ms/token | 출력 (RAM = NVMe) |
|---|---|---|---|
| CPU 전용, 예측기 | **54** | **114** | 일치 |
| GPU 혼합, 균등 선택 | 117 | 256 | 일치 |
| GPU 혼합, 예측기 | 234 | 304 | 일치 |

- 수정 뒤에는 GPU 혼합에서도 RAM 실행과 NVMe 실행의 출력이 같고, NVMe 실행의 RAM 상주량이 28.4 MiB로 CPU 전용과 같다.
- 예측 정확도(유지된 어텐션 질량)는 GPU 혼합 0.982, 오라클 0.985로 CPU 전용과 같은 수준이다.
- 느린 이유는 레이어마다 GPU와 CPU가 결과를 주고받으며 동기화하기 때문이다. 선택만 켠 GPU 혼합(117 ms)이 CPU 전용(약 46 ms)보다 토큰당 약 70 ms 느리다. 28개 레이어로 나누면 레이어당 약 2.5 ms다. 예측기를 켜면 근사 Q를 GPU에서 받아오는 동기화가 더해져 예측 비용이 3.0 ms/step에서 11.0 ms/step으로 늘었다.
- 참고로 KV까지 전부 GPU에 둔 일반 실행(`-ngl 99`)의 decode는 60 ms/token, CPU 전용 base는 48 ms/token이다. 이 보드에서는 decode에서 GPU가 CPU보다 빠르지 않다(README.md의 주파수 스윕에서도 최고 주파수 decode가 GPU 24.4, CPU 23.4 t/s).

## 의미

- KVSwap 오프로딩 실험은 CPU 전용으로 진행한다. GPU 혼합은 같은 작업을 더 느리게 하므로 의미 있는 운용점이 아니다.
- 보고서에는 "GPU와 함께 쓰는 구성을 시험했고, 통합 메모리 SoC에서 레이어별 CPU-GPU 동기화 비용 때문에 CPU 전용보다 느렸다"로 적을 수 있다.
- 논문처럼 어텐션까지 GPU에서 하려면 레이어별 마스크를 그래프 입력으로 따로 만들어야 한다. 이 경우에도 KV 뷰 전체를 레이어마다 GPU로 복사하므로, 선택 읽기는 디스크 읽기만 줄이고 메모리 복사량은 줄이지 못한다.
