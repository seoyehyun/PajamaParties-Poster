# 보고서용 보강 실험 결과 (Orange Pi 6 Plus, 2026-11-20~21)

report-experiment-plan.md의 E1~E9를 한 번에 돌린 결과다. 큐 스크립트는 [exp_queue.sh](../../code/scripts/exp_queue.sh)이고, E1~E8의 10개 단계가 11/20 20:29부터 11/21 01:50까지, E9 3단계와 e6_co 재측정이 그 뒤에 실패 없이 끝났다. 원본(실행별 폴더, jsonl, 로그)은 보드의 `/mnt/ssd/runs/q20261120/`에 있고 git에는 넣지 않았다. 이 폴더의 CSV는 그 요약이다.

**모든 값은 n=1이다.** 시간을 줄이려고 반복을 하지 않았고, 이미 n≥2로 잰 점은 다시 재지 않고 기존 값을 썼다(각 절에 출처 표시). 열 판정의 노이즈 폭은 반복이 없어서 최소값 5%를 쓴다. 예전 실험의 반복 간 편차는 열 면적 1~7%, TPOT 1% 안팎이었다.

## 1. E5: KV swap이 decode의 주파수 곡선을 바꾸는가 (C3)

조건은 11/14와 같다(Qwen3-1.7B Q4_K_M, 7,013토큰 프롬프트 + 2,000토큰 생성, ctx 10240, prefill은 기본 거버너, 첫 토큰부터 A720 고정). 이 단계는 TPOT과 사용률만 보고 열 꼬리는 3분으로 잘랐다. 실제 cpu6 주파수는 decode 내내 요청값과 같았다. 1500 MHz는 11/14 값이다(`phase_1500` n=2, `kvphase_1500` n=1). 1500의 RAM 사용률은 E6의 `phase_1500`에서 왔다.

| A720 MHz | RAM TPOT (ms) | swap TPOT (ms) | RAM 읽기 GB/s | swap 읽기 GB/s | RAM A720 util | swap A720 util | swap iowait | swap 디스크 util / MB/s |
|---|---|---|---|---|---|---|---|---|
| 1200 | 85.6 | 86.5 | 38.7 | 19.7 | 0.99 | 0.84 | 0.01 | 0.09 / 27 |
| 1500 | 78.8 (11/14) | 76.8 (11/14) | 41.9 (E6) | – | 0.99 (E6) | – | – | – |
| 1800 | 75.0 | 68.8 | 43.3 | 24.7 | 0.99 | 0.83 | 0.02 | 0.11 / 34 |
| 2200 | 73.6 | **65.6** | 43.6 | 26.5 | 0.98 | 0.82 | 0.02 | 0.12 / 36 |

prefill은 RAM 333초, swap 346~347초로 11/14와 같다.

**판정: "병목이 대역폭에서 연산 쪽으로 이동"을 지지한다.**

- 주파수 민감도 S = (TPOT₁₂₀₀ − TPOT₂₂₀₀)/TPOT₁₂₀₀ ÷ (2200−1200)/1200는 RAM 0.17, swap 0.29다.
- RAM은 1800 이후 거의 빨라지지 않는다(75.0 → 73.6). swap은 2200까지 계속 빨라진다(68.8 → 65.6). knee가 위로 이동했다.
- RAM의 DRAM 읽기는 39~44 GB/s로 포화 수준이다. swap은 20~26 GB/s로 절반이고, 주파수와 함께 늘어서 대역폭에 막혀 있지 않다.
- 디스크는 새 병목이 아니다. util 0.12 이하, iowait 0.02 이하다.
- 1200 MHz에서는 swap 이득이 없다(86.5 대 85.6). 주파수가 낮으면 둘 다 연산이 병목이라, KV swap의 TPOT 이득은 높은 주파수에서만 나온다.
- 미확인: swap의 A720 util이 0.82~0.84로 RAM보다 낮다. iowait가 아니므로 디스크 대기는 아니다. KV 선택과 재사용 단계의 스레드 동기화 대기로 추정하지만 확인하지 않았다.

## 2. E6: 사전 계산 테이블의 독립 검증 (C6)

테이블([precomputed-table.md](precomputed-table.md))을 만든 실행과 별개로 새로 쟀다. 기준선 대비 비율이다.

| 시나리오 | 설정 | 테이블 값 | 이번 측정 | 판정 |
|---|---|---|---|---|
| CPU 전용 7K | decode만 1500 (`phase_1500`) | 열 0.87, TPOT 1.05, TTFT 1.00 | 열 **0.88**, TPOT 1.05, TTFT 1.00 | 통과, 재현 |
| CPU 전용 7K | KV swap (`kv_default`) | 열 0.87~0.90, TPOT 0.90, TTFT 1.04 | 열 **0.88**, TPOT 0.90, TTFT 1.04 | 통과, 재현 |
| CPU+GPU 동시, 짧은 컨텍스트 | GPU 1000 + A720 1500 (`co_g1000_c1500`) | 열 0.74, GPU 0.83, CPU 1.12 | 열 **0.67 / 0.67**, GPU 0.83 / 0.83, CPU **1.10 / 1.11** (두 회차: `e6_co`, `e6_co2`) | CPU 작업 TPOT 제약(1.10)을 근소하게 넘어 탈락. 테이블의 "제약 1.15면 통과" 경계 그대로 |
| GPU 전용 | 건드리지 않음 | 0.99 | 재측정 안 함(검증할 이득이 없음) | |

naive TPOT은 74.6 ms로 11/14(74.9)와 같지만, 토큰당 열 면적은 6.30으로 11/14(6.81)와 7% 다르다. **열은 묶음 안의 기준선 대비 비율로만 쓴다.**

`e6_co`의 사용률 칸은 쓰지 않는다. decode 구간을 CPU 요청 4개가 끝난 시각 기준으로 잡아서, GPU 작업이 끝난 뒤의 구간이 들어갔다(`gpu_busy_d` 0.00). 코드를 고치고(a2241a8) 같은 두 설정을 `e6_co2`로 다시 쟀다. GPU 작업의 decode 구간에서 `gpu_busy` 1.00, GPU 호스트 코어 util 0.65~0.66, A720 util 0.93~0.94다. 이 시나리오의 A720 읽기(24~26 GB/s)는 CPU 요청 사이의 모델 로드 공백이 섞인 값이라 비교용으로만 쓴다.

## 3. E7: 긴 컨텍스트 동시 실행 + decode만 1500 MHz (C5, 테이블 빈칸)

CPU 작업(7K 프롬프트 + 3,000토큰, KV 위치가 변수)이 첫 토큰을 내면 GPU 작업(3,000토큰)이 시작한다. 새 설정 `ck_swap_g1000_d1500`은 첫 토큰부터 A720을 1500 MHz로 고정한다(전환은 첫 토큰 0.7초 뒤).

| 설정 | CPU 작업 TPOT | GPU 작업 TPOT | TTFT | 열 (요청 전체) | 열 (첫 토큰 이후) | 읽기 GB/s | A720 util | GPU busy |
|---|---|---|---|---|---|---|---|---|
| `ck_ram_gdef_cdef` (기준선) | 1.00 (81.3 ms) | 1.00 (73.9 ms) | 1.00 | 1.00 | 1.00 | 41.3 | 0.96 | 0.86 |
| `ck_swap_g1000_cdef` | 0.84 | 0.81 | 1.04 | 0.90 | 0.76 | 25.4 | 0.81 | 0.90 |
| **`ck_swap_g1000_d1500`** | **0.97** | **0.79** | **1.05** | **0.81** | **0.55** | 21.6 | 0.83 | 0.93 |

- swap/기본 행은 11/19 테이블 값(CPU 0.83, GPU 0.80, 첫 토큰 이후 0.76)을 재현했다.
- **테이블의 "decode만 1500은 미측정" 칸이 채워졌다.** 제약을 모두 지키면서 열이 0.81(첫 토큰 이후 0.55)로, swap만 켠 0.90/0.76보다 낮다. 요청 전체 1500 고정(11/19 `c1500`, TTFT 1.55로 탈락)의 열 이득 대부분을 TTFT 손해 없이 얻는다.
- ck 설정의 `switch_error_s`는 의미가 없어 CSV에서 비웠다(GPU 작업이 CPU 작업보다 약 55초 늦게 끝나서 계산이 어긋남).

## 4. NPU (E1, E2, E3, E1b)

모델은 Qwen2.5-0.5B int8 `.cix`(prefill S=256, decode P=255)이고 CPU, GPU 쪽의 Qwen3-1.7B와 다르다. NPU 호스트 프로세스는 cpu3(A520)에서 돌고, decode는 결과 한 줄당 32토큰이다.

### 4-1. 단독 주파수 스윕 (E1)

| NPU MHz | 400 | 600 | 800 | 1200 |
|---|---|---|---|---|
| decode t/s | 11.7 | 14.6 | 16.5 | 18.3 |
| decode NPU util | 0.82 | 0.77 | 0.74 | 0.72 |
| prefill t/s | 448 | 650 | 834 | 1116 |
| TTFT (256토큰 prefill) | 572 ms | 394 ms | 307 ms | 229 ms |

- 주파수 3배에 prefill은 2.49배, decode는 1.56배 빨라진다. **CPU, GPU와 같은 패턴(prefill은 연산, decode는 대역폭과 고정 비용)이다.**
- decode에는 토큰당 약 15.5 ms의 호스트 작업(입력 적재, 출력 읽기, argmax, KV 창 이동)이 주파수와 무관하게 들어간다. 이를 빼도 NPU 계산은 3배 주파수에 1.8배만 빨라진다.
- A720 주파수(1200~2200)와 GPU 주파수(350~1000)를 바꿔도 단독 NPU decode는 17.4~18.4 t/s로 변하지 않는다(교차 영향 없음).

### 4-2. 동시 실행 (E2)

슬로다운 = 동시 ms/token ÷ 단독 ms/token − 1(기존 CPU×GPU 표와 같은 방식).

| 조합 | NPU 슬로다운 | 상대 슬로다운 | NPU 호스트 ms/토큰 | A720 읽기 GB/s |
|---|---|---|---|---|
| NPU 단독 1200 | – | – | 15.4 | 0.3 |
| NPU 1200 + CPU 1200 | +2.7% | CPU +1.6% | 17.2 | 21.1 |
| NPU 1200 + CPU 2200 | **+16.6%** | CPU +1.2% | **22.9** | 27.5 |
| NPU 400 + CPU 2200 | +7.3% | CPU +1.1% | 22.6 | 27.9 |
| NPU + GPU (네 조합) | −1.9~+3.9% | GPU 0~1.2% | 15.7~16.2 | – |

- **NPU가 CPU 작업 때문에 느려지는 원인은 NPU 계산이 아니라 호스트 쪽이다.** CPU decode가 DRAM 읽기를 27.5 GB/s로 올리면 NPU 호스트 시간이 15.4 → 22.9 ms로 늘고, NPU 계산 시간은 39 → 41 ms로 거의 그대로다. 메모리 경합이 A520에서 도는 KV 입출력을 늦춘다.
- NPU와 GPU는 서로 거의 간섭하지 않는다.
- prefill 동시 실행은 모든 조합이 ±2.6% 이내다(호스트 시간도 토큰당 0.01 ms).

### 4-3. 세 자원 동시 실행 (E3, decode)

| NPU / A720 / GPU (MHz) | GPU 슬로다운 | CPU 슬로다운 | NPU 슬로다운 | 참고: CPU+GPU만, 11/13 GPU 슬로다운 |
|---|---|---|---|---|
| 1200 / 2200 / 1000 | +81.1% | +10.1% | +21.0% | +74.6% |
| 400 / 2200 / 1000 | +78.9% | +7.1% | +9.9% | +74.6% |
| 1200 / 1200 / 1000 | +35.7% | +12.8% | +12.5% | +19.6% |
| 400 / 1200 / 1000 | +29.6% | +11.1% | +6.3% | +19.6% |
| 1200 / 2200 / 350 | +29.7% | +4.9% | +16.2% | +36.2% |
| 1200 / 1200 / 350 | +6.5% | +6.8% | +5.7% | +2.8% |

GPU 손실의 대부분은 CPU 작업에서 온다(CPU+GPU만으로 +75%). NPU를 더하면 몇~16%p 늘지만, 참고 열은 다른 날(11/13) 측정이라 대략의 비교다.

### 4-4. NPU 열 면적 (E1b): 측정 불가

고정 작업량(120단위 = 3,840토큰) 후 꼬리까지의 열 면적이 토큰당 −0.31~+0.09 °C·s로 0 근처에서 부호가 바뀐다(CPU decode는 토큰당 약 5.6). 꼬리도 1초 안에 끝났다. **NPU의 발열은 1 °C 해상도의 열 존으로 볼 수 있는 크기보다 작다.** 이 방법으로는 NPU 주파수의 열 이득을 판단할 수 없다는 것이 결과다.

## 5. E4: CPU×GPU 동시 실행 4×4 (C2)

decode는 11/13에 없던 10칸을 새로 쟀고(각 칸의 단독 분모도 같은 묶음에서 잼), prefill은 4×4 전체를 쟀다.

**decode, GPU 슬로다운** (괄호는 CPU 슬로다운, *는 11/13 값)

| A720 \ GPU | 350 | 600 | 800 | 1000 |
|---|---|---|---|---|
| 1200 | +2.8%* (+1.2) | +6.7%* (+3.6) | +18.0% (+7.3) | +19.6%* (+6.6) |
| 1500 | +14.5% (+1.3) | +21.2% (+4.6) | +27.7% (+6.3) | +35.9% (+7.4) |
| 1800 | +22.4% (+0.9) | +35.7% (+3.4) | +45.6% (+4.6) | +54.2% (+5.6) |
| 2200 | +36.2%* (−1.4) | +55.8%* (−0.2) | +68.0% (+1.8) | +74.6%* (+1.5) |

- GPU 손실은 A720 주파수와 GPU 주파수가 둘 다 높을수록 단조롭게 커진다. CPU 손실은 7% 이하다.
- 이 단계의 `read_GBps_a720`(22~26 GB/s)은 llama-bench 반복 사이의 모델 로드 공백이 평균에 섞여 낮게 나온다(A720 util 0.70). 칸끼리의 비교에만 쓴다.

**prefill:** 16칸 모두 CPU 슬로다운 −0.1~+0.5%, GPU 슬로다운 −0.2~+0.4%다. **prefill 동시 실행에는 간섭이 없다.** 단독 민감도는 CPU prefill 13.0 → 7.2 ms/토큰(1200 → 2200), GPU prefill 158 → 55 ms/토큰(350 → 1000)으로 주파수에 거의 비례한다.

## 6. E8: KV swap의 간섭 감소, 다른 주파수 (C4)

[corun_kvswap.py](../../code/scripts/joint/corun_kvswap.py), 7K CPU 작업(RAM 또는 swap) 안에서 GPU 작업을 주파수별로 돌렸다.

| A720 / GPU (MHz) | GPU 슬로다운 RAM → swap | A720 읽기 GB/s RAM → swap |
|---|---|---|
| 1200 / 350 | +9.0% → +2.8% | 36.9 → 18.5 |
| 1200 / 800 | +23.9% → +12.9% | 35.3 → 18.4 |
| 1800 / 350 | +56.4% → +11.6% | 41.7 → 23.2 |
| 1800 / 800 | **+88.4% → +29.5%** | 41.4 → 24.8 |

11/19에 한 점(1500/1000)에서 본 효과가 네 점 모두에서 나왔다. A720 쪽 읽기가 절반으로 줄어든 것이 GPU 슬로다운 감소와 같이 간다. CPU 작업의 슬로다운 차이(−1~+8%)는 이 실험의 노이즈 바닥(같은 프로세스 안 단독 구간 간 최대 19%)보다 작아서 결과로 쓰지 않는다.

## 6b. E9: 작은 모델에서 KV swap 손익분기점

Qwen2.5-0.5B-Instruct Q4_K_M(가중치 0.49 GB, 24층, KV 헤드 2개 × head_dim 64, KV 한 행 128값)으로 컨텍스트를 바꿔 RAM(`naive`)과 KV swap(`kv_default`)을 비교했다. 1,000토큰 생성, 각 1회.

설정이 1.7B와 다른 점:

- 어댑터는 r=32(σ=4)를 썼다. 1.7B와 같은 σ=8(r=16)은 key 에너지 보존이 평균 0.81(최소 0.66)로 낮다. r=32는 0.90이다(1.7B r=128은 0.95). 보드에서 [make_kvswap_adapter.py](../../code/scripts/kvswap/make_kvswap_adapter.py)로 만들었다(C4 16개 × 2,048토큰).
- G=16, M=25다. 0.5B는 8칸 그룹이 2 KiB라 O_DIRECT 정렬(4 KiB)에 맞지 않는다. 선택 토큰 수는 400개로 1.7B(M=50 × G=8)와 같다.
- **0.5B의 품질은 재지 않았다.** 판정표의 품질 0.945는 1.7B 값이 입력된 것이라, 아래 판정은 속도와 열만 본 것이다.

| 컨텍스트 (프롬프트 토큰) | RAM TPOT | swap TPOT | TPOT 비율 | prefill 비율 | 열 비율 | A720 읽기 GB/s RAM → swap | swap 디스크 읽기 (1,000스텝) |
|---|---|---|---|---|---|---|---|
| 약 256 | 13.5 ms | 15.2 ms | **1.13** | 1.05 | 1.06 | 30.0 → 27.0 | 5.4 MiB |
| 약 4K | 19.3 ms | 17.0 ms | **0.88** | 1.09 | 0.93 | 25.4 → 24.2 | 0.8 MiB |
| 약 16K | 42.0 ms | **18.2 ms** | **0.43** | 1.03 | 0.94 | 47.0 → 23.8 | 0.8 MiB |

- **손익분기점은 256과 4K 사이다.** 256에서는 KV 전체가 창(W=256) 안에 들어가 선택할 것이 없고, 관리 비용만 13% 더해진다. 4K부터 이득이 나고 16K에서 TPOT이 절반 이하가 된다. 정확한 지점을 찾으려면 1K, 2K를 더 재야 한다.
- **이 모델에서 이득은 디스크 오프로딩이 아니라 선택적 attention에서 온다.** 4K와 16K에서 1,000스텝 동안 디스크 읽기가 0.8 MiB뿐이고(선택된 KV가 거의 모두 재사용 버퍼에 있음), 16K RAM의 decode는 attention이 커서 DRAM 읽기 47 GB/s, 42 ms까지 느려진다. swap은 약 660토큰만 읽어 컨텍스트와 무관하게 17~18 ms를 유지한다.
- 열 이득은 작다(0.93~0.94). 열 면적의 대부분이 prefill(16K에서 640~657초)에서 나오고, KV swap은 prefill을 줄이지 않기 때문이다.
- 1.7B(E5, 7K)와 비교: 1.7B는 7K에서 TPOT 0.90이고 디스크 읽기가 27~36 MB/s 있었다. KV 한 행이 8배 큰 모델이라 같은 선택량에서도 디스크로 가는 양이 많다.

## 6c. 테이블 칸 재측정: KV swap에서 decode만 1500 (n=2)

사전 계산 테이블의 "CPU decode, GPU 없음, KV swap → 기본" 칸은 11/14의 `kvphase_1500` 1회(열 0.904, `kv_default` 0.903)에 기대고 있었다. governor 실행(11/21)에서 이 칸 때문에 GPU 작업 사이 구간이 2.3 GHz로 돌아가 고정 1500보다 약 10 °C 뜨거웠고, E5에서도 KV swap의 열이 decode 주파수에 따라 단조로 늘었다(1200/1800/2200: 4.93/5.13/5.45). 그래서 11/14와 같은 조건(32,000자 프롬프트 = 7,013토큰, 2,000토큰 생성, ctx 10240)으로 두 설정을 2회씩 번갈아 다시 쟀다. 원자료는 보드의 `/mnt/ssd/runs/kvphase_ab_20261121`이다. naive는 돌리지 않았다(TPOT 비율은 11/14 naive 74.9 ms 기준).

| 설정 | TPOT | naive 대비 TPOT | 열(요청 전체, 토큰당) | prefill 열 | decode 구간 열 | 첫 토큰 이후 열 | decode 마지막 60초 zone8 | dT_ss |
|---|---|---|---|---|---|---|---|---|
| `kv_default` | 67.1 ms | 0.90 | 6.24 (6.09~6.39) | 8,479~8,550 | 3,245~3,343 | 3,637~4,184 | 64 °C | 25.8 |
| `kvphase_1500` | 76.7 ms | 1.02 | 5.94 (5.90~5.98) | 8,701~8,848 | 2,469~2,477 | 3,054~3,069 | 55 °C | 16.7 |
| 비율 | 1.14 | | **0.95** (r2끼리 0.98) | 1.02 | **0.75** | **0.78~0.84** | −9 °C | 0.65 |

열은 존 8, 단계별 값은 °C·s 합계다. `kv_default` r1은 꼬리가 기준선으로 돌아오지 않아(`tail_complete=0`) 첫 토큰 이후 값이 크게 나왔다. 꼬리가 완결된 r2끼리 비교한 값이 0.84다.

- **decode 단계의 열은 분명히 낮다.** decode가 14% 길어져도 그 구간의 열 합계는 25% 적고, 두 반복의 범위가 겹치지 않는다. TPOT은 naive 대비 1.02배로 제약(1.10배) 안이다.
- **요청 전체의 열 차이는 작다(0.95, 노이즈 폭 5% 경계).** 요청 전체 열의 약 70%가 두 설정에 공통인 prefill(347초)에서 나오기 때문이다. 11/14의 "이득 없음"(0.904 대 0.903)은 이 희석에 1회 측정의 흔들림이 겹친 결과로 보인다. 11/14의 `kvphase_1500` 6.16은 오늘 두 값(5.90, 5.98)보다 높고, `kv_default`는 6.15로 오늘 범위 안이다. dT_ss는 11/14(17.3 대 25.8)를 재현했다.
- **결론: 칸을 "decode만 1500"으로 바꾼다.** "최적" 정의(제약 안에서 열 최저)로 보면 첫 토큰 이후 기준으로도, 요청 전체 기준으로도 1500이 같거나 낮다. governor는 첫 토큰 이후에만 판단하므로 첫 토큰 이후 열이 맞는 기준이다.
- 고친 칸으로 governor를 다시 돌린 결과(n=1)는 [governor-lite.md](governor-lite.md) "재실행 결과"에 있다. governor가 decode 1.5 GHz 고정과 같은 열(기준선 대비 0.32 대 0.33)과 속도를 냈다.
