# GPU 전용 실행의 GPU, A720 주파수 열 A/B (Orange Pi 6 Plus, 2026-11-17~18)

gpu-axis-experiment-plan.md의 **S2(GPU 전용)** 를 돌린 결과다. 질문은 "GPU가 모델을 돌릴 때 GPU와 A720 주파수를 어떻게 정하면 열이 가장 낮은가"이다. 스크립트는 [thermal_ab.py](../../code/scripts/joint/thermal_ab.py)(`gnaive`, `g<GPU>_c<A720|def>` 설정). 원본은 `runs/thermal_gpu_s2/`(git 제외, 보드 시계 기준으로 11/11 날짜가 찍혀 있다).

|---|---|
| `thermal_ab_gpu_20261118_summary.csv` | 스크립트 리포트(설정별 평균, 판정) |

## 조건

- 모델 Qwen3-1.7B Q4_K_M, Vulkan 빌드(`build-vulkan`), `-ngl 99`, 호스트 스레드 1개를 A520 cpu2에 고정. 프롬프트 약 6,200자(prefill 728토큰), 생성 1,000토큰(decode 999토큰), ctx 4096. KV는 RAM(GPU 메모리)이고 **KV swap은 쓰지 않았다.**
- 설정 9개 × 2라운드 = 18회, 라운드마다 실행 순서를 돌렸다. 모든 실행의 기준 구간(45초)과 식는 꼬리는 기본 거버너 상태이고, 주파수는 요청이 도는 동안만 고정했다. 꼬리는 18회 모두 완료됐고 decode 구간도 모두 충분했다.
- `gnaive`: GPU devfreq와 A720 모두 기본. `g<G>_c<C>`: GPU를 G MHz로, A720 4개 정책을 C MHz로 고정(`def`는 기본 거버너). A720은 이 실험에서 유휴(호스트 스레드가 A520에서 돈다).
- 열 면적은 `gnaive`에서 가장 뜨거운 **존 12**(토큰당 1.71 °C·s)를 기준으로 했다. CPU 전용 실험의 가장 뜨거운 존은 8이어서 시나리오마다 다르다. 판정 기준은 앞과 같다(열 이득 > 노이즈 여유 5%, TPOT과 TTFT ≤ 1.10배).

## 해석

- **GPU 전용에서는 GPU 주파수를 낮출수록 열이 오히려 늘었다.** 최고 온도와 decode 중 온도(dT_ss)는 내려가지만(11.2 → 7.0 °C), 같은 작업을 더 오래 하느라 열이 쌓이는 시간이 길어져서 요청 전체의 열 면적은 커진다. 350 MHz에서 1.44배, 600 MHz에서 1.13배다. CPU 전용에서 1500 MHz 고정이 열을 크게 줄인 것(0.60~0.87배)과 반대의 결과다.
- **원인 추정(미확인):** 이 열 지표는 열 총량(에너지 대리)이어서, 작업이 느려지는 비율보다 전력이 줄어드는 비율이 작으면 총량이 늘어난다. 보드의 유휴와 정적 전력(GPU와 메모리를 켜 두는 것)이 커서 GPU 주파수를 낮춰도 전력이 그만큼 줄지 않는 것으로 보이지만, 전력 센서가 없어서 직접 확인하지는 못했다.
- **속도 제약도 걸린다.** 800 MHz 이하는 TPOT과 prefill이 모두 1.10배를 넘는다(1.20, 1.57, 2.61배). 열 쪽 결과와 무관하게 후보에서 빠진다.
- **A720 고정은 이득이 없었다.** 같은 GPU 주파수에서 A720을 800으로 고정한 설정이 기본 거버너보다 열이 낮지 않았다(1000 MHz에서 1.06 대 0.99, 800에서 1.10 대 1.09, 600에서 1.17 대 1.13, 350에서 1.49 대 1.44). 차이는 대부분 노이즈 폭 안이다. A720이 유휴일 때 기본 거버너도 이미 800 MHz에 있어서 고정이 더하는 게 없다고 본다.
- **결과적으로 GPU 지배 시나리오의 최적은 "GPU 최대(1000 MHz), A720 기본"이고, 이는 `gnaive`와 같다.** `g1000_cdef`는 `gnaive`와 TPOT, 열 모두 차이가 없다(기본 거버너가 이미 GPU를 1000 MHz까지 올렸다). 즉 이 시나리오에서는 주파수 조절로 얻을 수 있는 열 이득이 없었다.

## 사전 계산 테이블에의 의미

GPU가 지배 자원일 때 사전 계산 테이블은 다음과 같다.

| 지배 자원 주파수(GPU) | 최적 A720 | 근거 |
|---|---|---|
| 1000 MHz | 기본 거버너 | 열 0.99배, 속도 1.00배 |
| 800 MHz | 기본 거버너 | 열 1.09배(둘 다 naive보다 나쁨), TPOT 1.20배 |
| 600 MHz | 기본 거버너 | 열 1.13배, TPOT 1.57배 |
| 350 MHz | 기본 거버너 | 열 1.44배, TPOT 2.61배 |

- 모든 행에서 A720 설정은 기본 거버너 쪽이 같거나 낫고, 전체적으로는 **GPU를 최대로 두는 행만 `gnaive` 수준을 지킨다.** 열이 최저인 조합은 GPU 1000 MHz다.
- 이 결과를 CPU 전용의 결과와 합치면, 지배 자원에 따라 최적이 반대로 갈린다: CPU가 지배(decode, 메모리 대역폭이 병목)일 때는 A720을 1500 MHz로 낮추는 게 열을 줄였고(0.87배, TTFT 유지), GPU가 지배일 때는 GPU를 낮추는 게 해로웠다.

## 한계

- 요청이 하나(prefill 728토큰, decode 999토큰)이고 모델 하나다. 컨텍스트가 길어지거나 GPU 부하가 낮아지면 결과가 달라질 수 있다.
- 열 면적은 에너지의 대리 지표이고 전력 센서가 없다. 존 12가 가장 뜨거운 존이지만 모든 존의 평균도 같은 방향이다(최고 1.74배, 최저 0.98배).
- 반복은 설정당 2회다. 같은 설정의 두 라운드 차이가 5~15%여서, 1.10배 안팎의 비교(`g800`, `g1000`의 A720 800 대 기본)는 구분하기 어렵다.
- GPU 주파수는 devfreq `cur_freq` 기준이다. 요청한 값과 같은지는 짧은 검증 실행에서 확인했다(1000 MHz 고정 시 실행 중 샘플 전부 1000). A720 고정 구간의 실제 주파수는 따로 확인하지 않았다(유휴라서 영향이 작다고 보지만 미확인).
- KV swap은 이 시나리오에 넣지 못했다. `-ngl 99`에서는 KV 버퍼가 GPU 메모리에 있어 패치가 세그폴트(exit 139)로 죽고, `-nkvo`(KV를 CPU에 둠)로는 동작하지만 prefill 463 ms/tok, decode 781 ms/tok로 6.6배, 12배 느려서 쓸 수 없다. 호환성 확인용 짧은 실행이었고 한 번씩만 했다.
- CPU 전용 결과와 직접 비교하지 않는다. 요청 길이, 모델 위치, 기준선이 다르다.

## 다음 실험 후보

1. **CPU와 GPU가 한 요청을 나눠 처리하는 부분 오프로드**(`-ngl` 일부 레이어). 두 자원이 모두 일해서 A720 주파수가 의미를 가지는 유일한 조합이다. 이 실험에서 CPU 주파수가 지배 자원 판별에 영향을 주는지가 핵심이다.
2. GPU 전용에서 컨텍스트를 길게(예: 4K 이상) 해서 지배 자원이 바뀌는지 본다.
3. 전력 센서나 외부 측정이 가능해지면 열 면적과 비교한다.
